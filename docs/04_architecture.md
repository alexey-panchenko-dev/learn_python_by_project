# Архитектура проекта

## Поток зависимости

```text
route → service → repository → SQLAlchemy model → PostgreSQL
          ↓
     domain rules

Pydantic schema ← route → HTTP
```

Route знает HTTP, но не пишет SQL. Repository знает SQL, но не решает, чей сейчас
ход. Service управляет сценарием и транзакцией. Model отображает данные БД.
Schema задаёт внешний JSON-контракт.

## Зачем, если можно одним файлом

Для 30 строк один файл нормален. Разделение становится полезным, когда правило
используется из нескольких transport-слоёв, SQL меняется независимо от HTTP,
или части нужно тестировать отдельно. Цена слоёв — больше файлов и переходов.
Архитектура должна окупать эту цену.

## Domain error и HTTPException

Service поднимает `GameError`, потому что не обязан знать о HTTP. Route переводит
её в `HTTPException`. Тогда тот же service возможно вызвать из CLI или фоновой
задачи.

## Транзакция

Транзакция — группа изменений «всё или ничего». Service определяет границу
сценария и делает commit. `SELECT ... FOR UPDATE` блокирует строку игры на время
хода, чтобы два запроса не использовали одно и то же старое состояние.

## Не превращай шаблон в религию

Не нужен interface для каждого класса и generic repository ради формы. Сначала
назови реальную причину абстракции. Дублирование иногда дешевле неверной общей
абстракции.
