# Главный файл: как учиться по этому проекту

## Результат и срок

Твой срок — **8 недель по 1–3 часа в день, 5 дней в неделю**. Через восемь недель
ты должен уметь самостоятельно собрать API с CRUD, PostgreSQL, авторизацией,
бизнес-правилами, тестами и Docker. Цель не «узнавать знакомый код», а писать его
с пустого файла и объяснять каждое решение.

## Правила обучения

1. Не копируй блок, пока не можешь вслух предсказать его результат.
2. После чтения закрывай пример и воспроизводи его сам.
3. Ошибка — часть упражнения. Сначала прочитай последнюю строку traceback,
   сформулируй гипотезу, только затем меняй код.
4. Веди `MY_NOTES.md`: новая конструкция, своё объяснение, маленький пример.
5. Каждый день заверши одним зелёным тестом и коротким git-коммитом.
6. Не изучай весь Python заранее. Изучай конструкцию тогда, когда встретил её.
7. Если решение работает, спроси: где здесь HTTP, где правило, где хранение?
8. Не открывай Docker-эталон до собственной попытки.

## Цикл мышления для каждой задачи

Перед кодом запиши ответы:

1. **Контракт:** что приходит, что возвращается, какие ошибки возможны?
2. **Правило:** что системе разрешено и запрещено?
3. **Состояние:** какие данные нужны и кто ими владеет?
4. **Слой:** это HTTP, бизнес-логика или хранение?
5. **Проверка:** каким тестом доказать правильность?
6. **Крайние случаи:** пустое значение, повторный запрос, неверный id,
   конкурентный запрос, отсутствие прав.

Этот список важнее знания конкретного фреймворка.

## Неделя 1 — база Python на работающем коде

Прочитай `docs/01_python_syntax.md`, затем файлы `01_basic/app` в порядке из
локального README.

Самостоятельно:

- запусти сервер и вызови каждый endpoint в `/docs`;
- нарисуй на бумаге путь одного `POST /games`;
- без подсказки напиши функцию, считающую количество пустых клеток;
- добавь unit-тест этой функции;
- сломай один type hint и одно имя импорта, прочитай обе ошибки, верни обратно.

Критерий готовности: объясняешь `class`, `def`, `self`, type hints, list/dict,
comprehension, исключения, импорт и декоратор на примерах проекта.

## Неделя 2 — HTTP, Pydantic и CRUD

Прочитай `docs/03_http_fastapi.md`.

Не глядя в готовую реализацию создай рядом учебный endpoint заметок:

- `POST /notes`;
- `GET /notes` и `GET /notes/{id}`;
- `PATCH /notes/{id}`;
- `DELETE /notes/{id}`;
- Pydantic-проверки длины заголовка;
- ответы 201, 204, 404 и 422;
- минимум пять API-тестов.

Затем удали учебные notes или сохрани их в отдельной ветке.

## Неделя 3 — рефакторинг и архитектура

Прочитай `docs/04_architecture.md`. Возьми свой notes-код и раздели его на
schema, repository, service и route. Нельзя переносить код механически: рядом с
каждой функцией в заметках запиши, почему она принадлежит этому слою.

Сравни две версии крестиков-ноликов. Составь таблицу: проблема базовой версии →
решение production-версии → цена решения.

## Неделя 4 — SQL и PostgreSQL

Прочитай `docs/05_database.md`. Подними PostgreSQL известным тебе способом через
`docker run`, создай `.env` из `.env.example`, затем:

```powershell
cd 02_production
py -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -e . --group dev
Copy-Item .env.example .env
alembic upgrade head
fastapi dev app/main.py
```

Самостоятельно выполни SQL-запросы `SELECT`, `INSERT`, `UPDATE`, `DELETE` в
клиенте БД. Затем добавь к игре поле `title`: сначала ORM-модель и schema, потом
сгенерируй миграцию, изучи её, примени и протестируй.

## Неделя 5 — async, repository и транзакции

Проследи `POST /games/{id}/moves` от route до SQL. Объясни каждое `async`,
`await`, `yield`, dependency и commit. Напиши тесты для занятой клетки, чужого
хода, победы и ничьей. Затем реализуй endpoint списка только собственных игр.

Не добавляй `async` «потому что backend»: он нужен, когда операция ожидает I/O.

## Неделя 6 — пароли и JWT

Прочитай `docs/06_auth.md`. Нарисуй два разных потока: регистрация и запрос с
Bearer-токеном. Объясни, почему хеш — не шифрование и почему payload JWT нельзя
считать секретным.

Самостоятельно добавь endpoint смены пароля. Требования: старый пароль проверен,
новый имеет ограничения, хеш обновлён, есть успешный и неуспешные тесты.

## Неделя 7 — тесты, качество и Docker

Прочитай `docs/07_testing_debugging.md` и `docs/08_docker.md`.

- доведи покрытие важных правил до набора счастливых и ошибочных сценариев;
- запускай `pytest`, `ruff check .`, `ruff format --check .`;
- выполни `02_production/docker/student/README.md`;
- только после рабочей попытки сравни с `docker/solution`;
- объясни каждую строку своего Dockerfile и compose-файла.

## Неделя 8 — воспроизведение и итоговый экзамен

Создай пустую папку и за два вечера воспроизведи каркас API по памяти: config,
model, schema, migration, repository, service, route, test. Можно заглядывать
только в `docs/`, но не копировать исходники.

## Итоговое ТЗ: Habit Tracker API

Напиши проект полностью сам, без ИИ и веб-поиска. Разрешены только твои заметки,
папка `docs/`, официальные справки команд `--help` и уже установленный редактор.

### Функциональные требования

Пользователь может:

- зарегистрироваться, войти и получить JWT;
- создать привычку с названием, описанием и периодичностью `daily`/`weekly`;
- получить список своих привычек с пагинацией;
- получить, изменить и удалить только свою привычку;
- отметить выполнение привычки на конкретную дату;
- отменить отметку;
- увидеть текущую серию (`current_streak`) и лучшую серию (`best_streak`);
- получить статистику выполнений за диапазон дат.

### Правила

- email уникален, пароль хранится только как хеш;
- название содержит 1–100 символов;
- одна привычка не может иметь две отметки на одну дату;
- будущую дату отмечать нельзя;
- чужие привычки не видны и не изменяются;
- серия daily считается по последовательным дням;
- серия weekly считается по последовательным календарным неделям;
- удаление привычки удаляет её отметки;
- ошибки имеют корректные HTTP-коды и понятный `detail`.

### Технические требования

- FastAPI, Pydantic, PostgreSQL, SQLAlchemy 2 async и Alembic;
- разделение `routes → services → repositories → models`;
- настройки из окружения, секрет не хранится в Git;
- Dockerfile и compose для API и БД;
- unit-тесты расчёта серий и API-тесты главных сценариев;
- README с установкой, командами, схемой архитектуры и примерами запросов;
- `ruff check .` и `pytest` проходят;
- минимум две миграции: начальная и осмысленное изменение схемы.

### Запрещённые упрощения

- глобальные списки вместо БД;
- SQL прямо в routes;
- хранение готового streak без возможности корректно пересчитать его;
- один огромный `main.py`;
- тесты, которые проверяют только статус 200;

### Порядок реализации

1. Напиши user stories и таблицу endpoints.
2. Нарисуй таблицы `users`, `habits`, `completions` и связи.
3. Реализуй чистую функцию streak и сначала покрой её тестами.
4. Сделай миграции и repositories.
5. Сделай services и их правила.
6. Подключи routes и авторизацию.
7. Напиши ошибочные сценарии тестов.
8. Добавь Docker и README.
9. Проведи саморевью по требованиям, не по ощущению.

### Экзаменационный критерий

Проект завершён, когда новый человек может запустить его только по README, а ты
без кода перед глазами объясняешь путь запроса, границы транзакции, создание JWT,
назначение миграции и причину каждого слоя.
